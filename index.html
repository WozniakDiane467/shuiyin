四层概念各司其职 · 完整链路对照

四套概念一次讲透，搞清各自定位、不能互相替代：
CRUD = 业务动作统称（增删改查），不参与执行；
REST = 网络传输层（GET/POST/PUT/PATCH/DELETE），浏览器和服务器通信；
入参规范 = Path/Query/Body 数据分区，安全隔离；
SQL = 底层数据库语言（SELECT/INSERT/UPDATE/DELETE），读写硬盘。

四层一一对应对照表（核心背诵）

业务 CRUD 含义 REST 请求方式 标准入参存放 后端 SQL 语句
C Create 新增 POST 表单内容放 Body，无 Path ID INSERT
R Read 查询 GET ID 放 Path，筛选分页放 Query，禁止 Body SELECT
U Update 全量修改 PUT ID 放 Path，完整表单放 Body UPDATE（全字段覆盖）
U Update 局部修改 PATCH ID 放 Path，仅传变更字段 Body UPDATE（单字段）
D Delete 删除 DELETE ID 放 Path，无 Body DELETE

为什么要搞四层，不能合并成一套？

CRUD

只是"名词统称"，没有执行能力

好比吃饭（CRUD）只是描述行为，不能光说吃饭，还要出门下单（REST）、点什么菜（入参）、厨师做菜（SQL）。

REST

只管网络传输，碰不到数据库

浏览器只能发网络请求，没有权限、没有内网通道访问数据库，必须后端中转翻译 SQL。直接用 REST 删库 = 前端随便发 DELETE 清空全部数据。

入参规范

是安全隔离手段

如果不分 Path/Query/Body，密码、id 全部拼在网址，日志永久留存，隐私泄露、越权漏洞泛滥。

SQL

只在内网后端执行，外网隔离

数据库是核心数据存储，严禁外网直接访问，所以前端不能写 SQL，必须后端接收 REST 请求再翻译。

🚫 每层缺失会出现的重大问题：
没有 CRUD：团队沟通无统一术语，需求看不懂；
没有 REST 分层请求（全用 POST）：无法批量拦截高危接口，缓存失效；
没有 Path/Query/Body 规范：参数乱放，明文泄露，越权漏洞满天飞；
没有 SQL 隔离前端直连数据库：任何人前端写 DELETE 清空全表，数据永久丢失。

💡 关键分界线：前端可见 = CRUD、REST、入参；前端完全看不见 = SQL（仅后端代码存在，浏览器拿不到）。

易混点辨析

误区 1

DELETE 请求 = 数据库 DELETE SQL？

❌ 错。DELETE 只是浏览器发的网络标识，没有任何删数据能力；只有后端执行 DELETE FROM... 才会真正删库。

误区 2

CRUD 可以直接写接口？

❌ 错。CRUD 是业务叫法，接口必须遵循 REST 名词 URL 规则。

误区 3

GET=SELECT 就能一套搞定？

❌ 错。GET 只是网络只读标记，拿不到数据还是要后端写 SELECT 查询数据库。

第三部分 · SQL 通俗大白话

SQL = 结构化查询语言

SQL = Structured Query Language，专门用来和数据库对话的「语言」，只有数据库能听懂。前面讲的 user 用户表、article 文章表，想查数据、新增、改数据、删数据，不能直接操作数据库文件，必须写 SQL 指令发给数据库。

💬 类比：前端写 JS、后端写 TS 是和服务器对话；写 SQL 是和数据库服务器对话。

四类核心 SQL 指令（对应 REST 四种请求）

SELECT · 查询

对应前端 GET 请求

SELECT id, title, author_id FROM article;

从 article 表查出 id、标题、作者 ID

INSERT · 新增

对应前端 POST 新增

INSERT INTO article(title, author_id) VALUES("春天游记", 5);

新增一篇文章，作者 id=5

UPDATE · 修改

对应 PUT / PATCH

UPDATE article SET title="新标题" WHERE id=12;

WHERE id=12 是关键，不加会全表清空

DELETE · 删除

对应 DELETE 请求

DELETE FROM article WHERE id=12;

不加 WHERE 整张表清空，线上重大事故

一对多关联 SQL（用户表 + 文章表）

需求：查出文章 + 对应作者昵称，需要关联两张表

SELECT a.id, a.title, u.name FROM article a LEFT JOIN user u ON a.author_id = u.id;

a.author_id = u.id 就是一对多外键关联，后端执行这条 SQL，才能把作者昵称一起查出来给到前端列表。

🚨 学生高频误区：
① 前端不能写、不能直接执行 SQL！SQL 只能写在后端代码里，数据库在内网，浏览器访问不到；
② AI 经常生成不带 WHERE 的 UPDATE/DELETE SQL，线上一执行全表清空，重大数据漏洞；
③ 不能用 slug 写关联查询，SQL 关联必须用数字 id，字符串匹配慢、容易出错。

第四部分 · WHERE 安全演示

WHERE 缺失 = 炸库

WHERE 翻译：条件、筛选范围。写 UPDATE/DELETE SQL 时，WHERE 用来告诉数据库：只对"满足这个条件的那一行/几行"做修改、删除操作。没有 WHERE = 整张表全部数据改动/删除。

底层逻辑：数据库默认规则

⚠️ UPDATE、DELETE 属于高危写入操作，数据库不会自动识别你只想改/删一条。只要你不给出筛选条件（WHERE），它默认作用于当前表全部行。
SELECT 查询无所谓，只看数据不会破坏内容，所以 SELECT 不带 WHERE 没事；
但改、删数据两条语句，WHERE 是强制安全屏障。

随堂检测

四层对照思考题

1. CRUD、REST、入参、SQL 四层各自负责什么？为什么不能合并？+

CRUD 是顶层业务统称（增删改查），只描述行为不参与执行；REST 是网络传输层，规定用 GET/POST/PUT/PATCH/DELETE 通信；入参规范是 Path/Query/Body 数据分区，安全隔离；SQL 是底层数据库语言，读写硬盘。不能合并：CRUD 只是文字没执行能力；REST 只管网络碰不到数据库；入参规范是安全手段不分层就泄露隐私；SQL 只在内网后端执行外网隔离。好比吃饭：CRUD 是描述吃饭行为，REST 是出门下单，入参是点什么菜，SQL 是厨师做菜，四步缺一不可。

2. DELETE 请求等于数据库 DELETE SQL 吗？为什么？+

不等于。DELETE 请求只是浏览器发的网络标识，没有任何删数据能力，数据库看不懂 HTTP 请求。只有后端接收到 DELETE 请求后，翻译成 DELETE FROM article WHERE id=10 这条 SQL，发给数据库执行，才会真正删除硬盘里的数据。前端不能直接执行 SQL，数据库在内网浏览器访问不到，必须后端中转翻译。所以 DELETE 请求是网络层指令，DELETE SQL 是数据库层指令，两者完全不同层。

3. WHERE 子句为什么不能丢？举例说明无 WHERE 的后果。+

WHERE 用来限定操作范围，告诉数据库只对满足条件的行做修改/删除。没有 WHERE 数据库默认作用于整张表全部行。例如 DELETE FROM article WHERE id=66 只删 id=66 这一条；如果写成 DELETE FROM article（无 WHERE），数据库会把 article 表里所有文章全部删掉，线上执行直接丢全部业务数据无法恢复。UPDATE 同理：UPDATE article SET title="新标题"（无 WHERE）会把整张表每一篇文章标题全部统一改成这一句，历史内容全部报废。AI 生成 SQL 经常漏写 WHERE，是重大数据漏洞。

4. 完整全栈链路中 SQL 处在哪个环节？前端能直接执行 SQL 吗？+

SQL 处在后端和数据库之间的环节。完整链路：前端点击按钮发 fetch → 后端接收请求、鉴权校验 → 后端写 SQL 发给数据库 → 数据库执行 SQL 返回数据 → 后端包装成 code/msg/data 给前端。前端不能直接执行 SQL，因为数据库在内网，浏览器访问不到，必须后端中转。SQL 是后端和数据库沟通的唯一桥梁，前端永远碰不到 SQL 语句，前端只发 REST 请求，后端接收后翻译成 SQL 操作数据库。

5. C/R/U/D 分别对应什么 REST 方式、入参位置、SQL 语句？+

C Create 新增 → POST 请求，表单内容放 Body 无 Path ID，SQL 用 INSERT INTO。R Read 查询 → GET 请求，ID 放 Path 筛选分页放 Query 禁止 Body，SQL 用 SELECT。U Update 全量修改 → PUT 请求，ID 放 Path 完整表单放 Body，SQL 用 UPDATE 全字段覆盖。U Update 局部修改 → PATCH 请求，ID 放 Path 仅传变更字段 Body，SQL 用 UPDATE 单字段。D Delete 删除 → DELETE 请求，ID 放 Path 无 Body，SQL 用 DELETE FROM WHERE id。四层一一对应，各司其职。
